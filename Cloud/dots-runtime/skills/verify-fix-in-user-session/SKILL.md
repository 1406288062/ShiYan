# 在用户实际使用的地方验证修复

## 先列出所有副本
- 动手前列出能提供这项功能的所有副本，例如服务器上运行的那份、代码仓库那份、打包进桌面 App 的那份。
- 逐个查文件内容和版本标记，写下哪些副本已经有修复、哪些没有。
- 没核对过就当作没同步；服务器上改了不代表桌面 App 或另一个仓库也改了。
- 自己更新不了的副本，告诉用户还差哪些，不要报告为全部完成。

## 网页修复先看缓存
- 测试前看改动资源的缓存头和版本参数（例如长 max-age、固定的 ?v=）。
- 资源被缓存时更新版本参数，并确认新地址返回的是新代码。
- 用户的页面是修复前打开的，就请用户刷新。
- 测用户实际打开的地址；自己重新下载到新文件不等于用户页面已经是新的。

## 远程检查先认准设备
- 用海绵宝宝 list_devices 列出设备，按名称、系统、设备 ID 对上用户说的那台再执行。
- 注意同名不同 ID 的设备，排除已失效的。
- 看清结果是哪台设备返回的，答错设备就在正确的设备上重做。

## 在用户的环境里验证后才说“好了”
- 在用户会用的环境（用户的浏览器页面、已安装的 App）里跑一遍主要流程，再说修好了。
- 服务器上的检查、下载的文件、你自己浏览器里的测试都只算准备工作，汇报时要这样标明。
- 用户环境验证不到时，明确说哪些验证了、哪些还没验证，此时不要说“已修复”。
- 用户仍看到旧问题时，从副本、缓存、会话三处重新查起，不要重复之前的结论。
